# Codebase-signal ablation on SWE-bench (invasiveness prediction)

Generated by `backend/scripts/swebench_validation.py` (deterministic, seed 42).
Question: does predicting **how invasive** a change is (files touched by
the real gold patch) get better when issue text is combined with codebase
signals at the base commit, versus issue text alone?

## Method

- Ground truth from each instance's `patch` (unified diff): `files_touched`,
  new/modified/deleted files, added/removed lines. Patches are labels only,
  never features.
- Primary metric: MAE of `files_touched` under 5-fold CV (identical seeded folds
  for both arms). Targets are modelled as `log1p`, predictions clipped to >= 1.
- Arms: (1) text-only deterministic features of `problem_statement` (size,
  structural counts, 25 keyword counts, path/module tokens, repo one-hot);
  (2) the same plus codebase features at `base_commit`: fan-in of modules
  mentioned in the issue text, radon cyclomatic complexity / LLOC of the
  mentioned files, 180-day churn and distinct authors of those paths, plus
  repo-level activity at the base commit. Model: Ridge(alpha=1) on
  StandardScaler; HistGradientBoosting reported as a robustness check.
- Decision gate pre-registered before running: **IMPROVED** iff the upper
  bound of the 95% paired-bootstrap CI of (MAE_codebase - MAE_text) is < 0
  **and** the relative MAE reduction is >= 1%; otherwise NOT IMPROVED
  (point estimate >= 0) or INCONCLUSIVE.

## Data

- Source: HuggingFace `princeton-nlp/SWE-bench`,
  `test` split; 2294 usable instances,
  12 repos. Command: `scripts/swebench_validation.py --dataset full --max-instances 0 --subset-repo sympy/sympy --subset-max-instances 150 --write`.
- Repo distribution (top): django/django 850, sympy/sympy 386, scikit-learn/scikit-learn 229, sphinx-doc/sphinx 187, matplotlib/matplotlib 184, pytest-dev/pytest 119, pydata/xarray 110, astropy/astropy 95.
- Primary target stats (full set): mean files_touched=1.66,
  median=1, max=31,
  multi-file rate=24.9%, adds-new-file rate=1.7%.
- Subset for the ablation: `sympy/sympy` (single repo, cloned with
  `--filter=blob:none --no-checkout`, blobs fetched lazily per base commit),
  n=150; ground truth mean=1.97, max=21.
- Codebase feature coverage on the subset: mentions of existing modules/files
  in issue text 47/150, fan-in fired
  35, complexity fired 47
  (radon installed),
  extraction failures 0.

## Decision gate

Paired MAE difference (text+codebase - text-only): **+0.0708 (+5.4%)**, 
95% bootstrap CI **[+0.0223, +0.1191]**.

**Result: NOT IMPROVED (codebase arm equal or worse)**: text-only MAE 1.318 vs text+codebase MAE 1.389 on n=150 sympy/sympy instances.
Robustness (HistGradientBoosting): 1.273 -> 1.274 (+0.001, same direction as Ridge).

## Leakage controls

- Features never read the patch; `patch` is used only to compute labels, and
  `hints_text` is ignored entirely.
- Codebase features are read at the instance `base_commit` via git objects;
  churn/author windows use `--since=<base_date - 180d> <base_commit>`, which
  cannot reach commits after the base commit.
- File paths mentioned in issue text are only kept as features if they exist at
  the base commit (existence check against `git ls-tree <base_commit>`).
- Repo one-hot categories and feature lists are label-independent (count-based).

## Domain mismatch

SWE-bench instances are open-source Python libraries (django, sympy, sklearn,
sphinx, matplotlib, pytest, ...). The product's domain is B2B SaaS delivery
estimation. Nothing here validates SaaS performance directly: results test the
mechanism (issue text + repo signals carry invasiveness signal), not the product
domain. Absolute MAE values should not be transferred to SaaS planning.

## Limitations

- SWE-bench Lite (300) was checked and rejected for the primary target: all 300
  Lite patches touch exactly one file, so MAE(files_touched) has no variance there;
  the full test split (2294) is used instead. Lite is a valid source of the
  self-test rows.
- Codebase features only fire when the issue text mentions module/file tokens
  (47 of 150 subset rows);
  for the rest the codebase arm falls back to repo-level activity features.
- Radon complexity is optional; without it those columns are zeroed (stated above).
- Fan-in is an import-occurrence count over absolute imports in `.py` files at the
  base commit (relative imports are missed).
- HistGradientBoosting rows are robustness checks only; the gate uses Ridge.

## Multi-file refinement (2026-10-17)

Why: 1723 of 2294 full-split patches (75.1%) touch exactly one file, so the
original MAE target is near-degenerate. This refinement re-runs the ablation on
the variance subset (`files_touched >= 2`, n=571) and on two alternative
patch-derived targets (`modified_files`, `added_lines`). The section above is
kept unchanged; this is a refinement, not a retraction.

### Method delta

- `--min-files 2`: the variance subset and the ablation subset keep only
  patches touching >= 2 files (default 0 = original behaviour).
- `--target files|modified|added_lines|all`: regression-target switch; labels come
  from the same patch parser. Same seeded 5-fold CV, same features, same Ridge/HGB;
  `log1p` targets, predictions clipped to >= 1 (`files`) or >= 0 (others).
- Codebase arm spans several repos, one blob-filtered `--no-checkout` clone each
  (per-instance checkout at `base_commit`, exactly as before).
- Extra baselines: per-fold median of the training subset and constant `always-2`.
- Leakage controls unchanged from the section above (features never read the patch;
  `hints_text` ignored; all codebase reads are at `base_commit`).

### Data

- Variance subset (`files_touched >= 2`, all repos, text-only): n=571,
  repos: django/django 182, sympy/sympy 94, scikit-learn/scikit-learn 53, sphinx-doc/sphinx 51, pydata/xarray 45, matplotlib/matplotlib 43, astropy/astropy 27, pytest-dev/pytest 26.
- Codebase ablation subset: n=132 (sympy/sympy 94, pytest-dev/pytest 26, psf/requests 12).
- Codebase feature coverage: mentions of existing modules/files in issue text
  38/132, fan-in fired 21, complexity fired 37 (radon installed), extraction failures 0.

### Decision (multi-file subset)

Target `files`, n=132, paired MAE difference (text+codebase - text-only): **-0.0954 (-2.8%)**, 95% bootstrap CI **[-0.5447, +0.2380]**.

**Result: INCONCLUSIVE**: text-only MAE 3.356 vs text+codebase MAE 3.260 on n=132 instances (CI includes 0, point estimate negative).
Directionally the codebase arm is better, but the pre-registered gate is not met;
treat this as a weak signal needing more instances, not as an improvement. The gate
is not met for any of the three targets, so the original negative result is not
overturned by this refinement.

The multi-file-vs-single-file binary classification is only meaningful on the full set
(kept above); on this subset it is degenerate (all positives).

### Caveats

- Small n (single-repo families, 571 variance rows, 132 codebase rows) and OSS-only
  domain: magnitudes should not be transferred to B2B SaaS estimation.
- Codebase features only fire when the issue text resolves to existing modules/files;
  the mention subgroup is reported per target where n >= 20.
- `modified_files` can be 0 (new-file-only patches) and `added_lines` is heavy-tailed;
  the always-2 baseline is shown for comparability, the median baseline is the fairer one.
- Ridge on `added_lines` is unstable (log1p inversion of extrapolated predictions can
  blow up on heavy-tailed rows; the subgroup line is flagged). HGB and the median
  baseline are the robust rows for that target. The codebase arm does not beat the
  median baseline on any target.
- Rank signal on the variance subset is ~0 for `files`/`modified` (-0.02/-0.00) and
  weakly positive for `added_lines` (+0.19) under the text-only arm.
