# End-to-end replay: extraction nulls and the missing-data mechanism

Generated by `backend/scripts/endtoend_null_prior.py` on 2026-10-24.
Deterministic given the committed extraction cache
(`data/endtoend_extractions.json`, DeepSeek, temperature 0, single sample) and
the recorded features in `data/synthetic_history.csv`.

**Question.** The standard walk-forward replay predicts each project from its
**recorded** feature vector, which is an oracle upper bound. What happens when
the estimator receives the LLM's extracted features instead — and, crucially,
what prior should be used for the features the extractor left unresolved?

## The key fact

An extraction `null` means "the request did not mention this feature". It is
**not** a random coin flip. In the committed cache:

| | |
|---|---:|
| P(feature = 1 \| null) | **4.1%** (100 / 2,436 null cells) |
| P(feature = 1), marginal | **25.2%** (863 / 3,420 cells) |

Per-feature null-conditioned rates range from 1.7% (multi-currency) to 8.5%
(data migration). Sampling a null at the marginal prevalence therefore invents
capabilities that are almost never present.

## Method

- **Extraction**: production path (`extract_features`) over the 228 completed
  demo emails (DeepSeek). The result is cached per `project_id`; `null` means
  the email did not state the feature.
- **Replay**: chronological walk-forward. The model is trained on rows
  `1..i-1` using their recorded features and predicts row `i` from the extracted
  vector. No future information is used.
- **Strategies at prediction time**:
  - `zero-fill`: unresolved features are set to 0;
  - `global`: the previous implementation, sampling each null at the marginal
    training prevalence;
  - `conditional`: sampling each null at `P(feature=1 | null)`, estimated
    walk-forward from earlier rows (small-sample fallback: overall null rate);
  - `oracle`: the true vector (upper bound).
- **Question loop**: for the conditional arm, the top-k unresolved features are
  ranked by their marginal effect on P50 and filled with their true values
  (oracle answers, an upper bound on a real user); the remaining nulls still use
  the conditional prior.
- 2,000 Monte Carlo draws per prediction; the model is Ridge (α=0.3) on log-days
  with the same out-of-fold residual bootstrap as the product.

## Results (218 steps)

| Strategy | MAE (days) | Coverage | Rel. width |
|---|---:|---:|---:|
| Zero-fill | 21.34 | 74.3% | 0.83 |
| **Global prevalence (previous)** | **49.64** | **55.5%** | **1.74** |
| **Conditional prior (4.1%)** | **20.48** | **85.3%** | **1.16** |
| Oracle features | 17.36 | 86.7% | 0.83 |

**Question loop (conditional prior, oracle answers):**

| Answers | MAE (days) | Coverage | Rel. width |
|---|---:|---:|---:|
| 0 | 20.48 | 85.3% | 1.16 |
| 5 | **17.99** | 85.3% | 0.86 |
| 10 | 17.46 | 83.0% | 0.81 |
| 15 | 17.46 | 84.9% | 0.83 |

## Reading

1. **The global prior is harmful on the real path.** It turns a 21.34-day
   baseline into a 49.64-day one: 71.2% of cells are unresolved and the marginal
   prevalence is six times the null-conditioned rate.
2. **Zero-fill is a strong simple baseline** (21.34 / 74.3%), but it
   under-covers and treats the 4.1% positive nulls as absent.
3. **The conditional prior recovers both accuracy and coverage** (20.48 / 85.3%)
   with a narrower interval than the global sampler, within 3.1 days of the
   oracle.
4. **Five answered questions close most of the remaining gap** (17.99 / 85.3%),
   close to the oracle (17.36 / 86.7%). The question loop is the mechanism that
   supplies the facts the request omitted.
5. **The random-mask ablation was the wrong mechanism.** Under uniform masking
   (the MCAR regime), the independent sampler covers 85.6%/85.2% while zero-fill
   covers 61.2%/39.3% (see `docs/MC_ABLATION.md`). Both results are correct for
   their own regime; deployment is the extraction-null regime.

## Caveats

- The answers in the question-loop ablation are **oracle answers**, not real
  users; they are an upper bound.
- The corpus is synthetic (240 projects, 228 completed). The extraction is one
  DeepSeek sample; provider updates can change it.
- Training uses the recorded features, not extracted ones; this isolates
  extraction error at inference.
- The product now loads `data/null_prior.json` (built by
  `backend/scripts/build_null_prior.py`) and passes it to `estimate_mc`. A
  deployment without the file falls back to the marginal prevalence (legacy
  behaviour); the file is committed for the demo.
