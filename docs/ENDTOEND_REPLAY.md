# End-to-end replay: LLM-extracted features and the question loop

Generated by `backend/scripts/endtoend_replay.py` on 2026-10-24.
Deterministic given the committed extraction cache
(`data/endtoend_extractions.json`, DeepSeek, temperature 0, single sample).

**Question.** The standard walk-forward replay predicts each project from its
**recorded** feature vector, which is an oracle upper bound: the extraction step
is never in the loop. What happens when the estimator receives the LLM's
extracted features instead, and how much does the question-answering loop
recover?

## Method

- **Extraction**: the production path (`extract_features`) is run over the 228
  completed demo emails with the configured provider (DeepSeek). The result is
  cached per `project_id`; `null` means the email did not state the feature.
- **Replay**: chronological walk-forward (train on rows `1..i-1` using their
  recorded features, predict row `i`). At prediction time the row's **extracted**
  vector is used; unresolved features are handled by the Monte Carlo sampler
  (2,000 draws, fixed seed). No future information is used.
- **Question-loop ablation**: for each test row, the top-k unresolved features
  are ranked by their marginal effect on P50 (the product's VoI heuristic) and
  filled with their true values — an **oracle answerer**, i.e. an upper bound on
  what a real user could supply. The remaining unknowns still go through Monte
  Carlo.
- **Metrics**: MAE and median absolute error (days), empirical P10–P90 coverage,
  relative interval width `(P90-P10)/P50`, and the number of unresolved cells.

## Results (218 steps)

| Condition | MAE (days) | MedAE | Coverage | Rel. width | Unknown cells |
|---|---:|---:|---:|---:|---:|
| Recorded features (oracle upper bound) | **17.36** | 9.20 | **86.7%** | 0.83 | 0 |
| Extracted, 0 answers | **49.64** | 46.40 | **55.5%** | 1.74 | 2,319 |
| Extracted + 5 oracle answers | **20.24** | 14.55 | **82.1%** | 1.08 | 1,229 |
| Extracted + 10 oracle answers | **17.35** | 8.85 | **83.9%** | 0.83 | 240 |
| Extracted + 15 oracle answers | **17.46** | 9.30 | **84.9%** | 0.83 | 0 |

Extraction quality on these 228 emails: micro precision/recall/F1 =
**0.987/1.000/0.993** on resolved cells (the standard micro-F1, which counts
unresolved positives as misses, is **0.933** on the 236-email evaluation in
`docs/EXTRACTION_EVAL.md`). **71.2%** of the 15×228 feature cells are unresolved;
no email produced an all-null vector.

## Reading

1. **Extraction alone is not enough.** With no questions answered the pipeline is
   worse than the simulated team baseline (49.64 vs 32.93 days MAE) and coverage
   collapses to 55.5%: the email simply does not state most features, and
   sampling all of them from prevalence widens the interval without sharpening
   the median.
2. **The question loop is the mechanism that closes the gap.** Five answered
   questions reduce MAE to 20.24 days and restore 82.1% coverage; ten answers
   reach 17.35 days and 83.9%, essentially the oracle result.
3. **The residual gap at 15 answers is extraction error.** Resolving all unknowns
   gives 17.46 days / 84.9% instead of 17.36 / 86.7%, because the extractor
   resolved a few features incorrectly (0.993 F1 on resolved cells, not 1.0).
4. **Practical implication.** The product's value is not "the LLM reads the email
   and outputs a number"; it is the combination of evidence-backed extraction,
   a small calibrated model, and a short, high-impact question loop.

## Caveats

- The answers are **oracle answers**; real users will be slower and sometimes
  wrong, so the 5/10/15-answer rows are upper bounds on the loop.
- Extraction is a single DeepSeek sample at temperature 0; provider updates can
  change it. The cache is committed for reproducibility, not as a claim of
  run-to-run stability.
- The corpus is the synthetic demo (240 projects, 228 completed); the real-data
  check on JOSSE is separate (`docs/MC_ABLATION.md` covers the missing-feature
  ablation; the JOSSE result is reported in the paper draft).
- Training uses the recorded feature vectors, not extracted ones; this isolates
  extraction error at inference. An end-to-end run that also trains on extracted
  features would compound the error and is not reported.

## Reproduce

With the committed cache (no API calls):

```bash
cd backend
PYTHONPATH=. python scripts/endtoend_replay.py --answers 0 5 10 15
```

To re-extract from scratch (needs `DEEPSEEK_API_KEY`, ~$0.2, ~10 minutes):

```bash
cd backend
PYTHONPATH=. python scripts/endtoend_replay.py --refresh --answers 0 5 10 15
```

Files: `backend/scripts/endtoend_replay.py`,
`data/endtoend_extractions.json`, `data/endtoend_replay_results.json`.
