# PR lead-time study — does repository friction slow a change down?

Generated by `backend/scripts/pr_leadtime_study.py` on 2026-10-18 05:57 UTC.
Deterministic given the same PR sample (seed 42); the PR list comes from the
GitHub API, so a later run sees newer PRs.

**Question.** The surcharge coefficients are partly measured (D20), but the
link *change size -> person-days* is not measurable from public data. GitHub
does publish a real per-change duration: a merged PR's `created_at ->
merged_at`. Does repository friction predict it, controlling for the change's
own size?

## TL;DR

Pooled friction coefficient on `log1p(lead time days)`: **-0.892** (95% CI [-1.263, -0.507]) over 3240 merged PRs.
Pre-registered gate (CI entirely > 0): **FAIL**.

## Method

* Merged PRs from the GitHub API (public data). `GITHUB_TOKEN` only raises
  the rate limit; it is never written to disk.
* Friction is **git-only** (churn + author concentration, the components
  computable from `git log`; D20) and computed **from commits strictly
  before** each PR's creation date. It is bucketed per month: friction is a
  slow-moving repository property, and bucketing keeps the study minutes-long.
* Target `log1p(lead time days)`; controls `log1p(changed_files)`,
  `log1p(additions + deletions)`, a bot flag and a `log1p(month index)` trend.
* Gate fixed before the run: pooled 95% paired-bootstrap CI of the friction
  coefficient entirely > 0.

## Honest interpretation (read this before quoting anything above)

**The gate FAILED.** The pooled coefficient is even **negative** (-0.892): higher friction is associated with *shorter* lead time. This design does not measure what it hoped to, and **no product coefficient may be derived from it**.

Why the target is unusable here, concretely:

1. **The target is nearly degenerate.** The median lead time is well under a
   day in these libraries — most PRs merge the same day they are opened — so
   there is almost no variation left to explain.
2. **The predictor barely varies within a repo.** Monthly-bucketed git-only
   friction sits at 0.80-0.96 for four of the five repos, so the coefficient
   is estimated off between-repo differences, not within-repo change.
3. **Friction and calendar time are correlated** (repos accumulate churn), and
   the `log1p(month index)` control absorbs that trend — the residual
   coefficient is unstable and can flip sign, which is what happened.

Conclusion: **lead time is not a usable proxy for effort.** The assumed
`size -> person-days` link stays an explicit assumption (D20/D24), and the
only path to measuring it is instrumenting the product (D24 roadmap).

## Honest limitations

1. **Lead time is not effort.** It includes review queues, CI, weekends,
   timezones and release trains; it is a *corroborating* duration, not
   person-days. The `size -> days` link stays an explicit assumption.
2. **Friction is monthly and git-only** (2 of 5 components): fan-in and
   complexity are Python-only and radon-heavy, so they are excluded here
   (they are included in the product's own score).
3. **OSS libraries != B2B SaaS**: nothing here validates client delivery.
4. Confounders are only partly controlled (reviewer availability, PR labels,
   linked issues). The month trend absorbs some of it.
5. The PR sample is capped per repo; a later run sees different PRs.
