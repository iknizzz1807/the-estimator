What it does NOT establish: **person-days** — see the honest limitations.

## Method

* Commits from `git log --no-renames --name-only`, chronological. The last
  40% are targets; earlier commits are history only.
* **Friction is computed from history strictly before each target** —
  per-file prior commit counts, prior author sets, and a
  6-month churn window. No leakage.
* It uses the **product's own constants**: `CHURN_SATURATION_COMMITS`,
  `FRICTION_WEIGHTS`, and the same saturating-normaliser / weighted-mean
  formula as `app.services.codebase.compute_friction`.
* Only 2 of the product's 5 components are computable from git alone
  (`churn`, `author_concentration`); `fan_in`/`complexity` need a checkout
  plus radon and `coverage` needs a report. The score is renormalised and
  labelled **git-only friction** throughout.
* Controls in the regression: log prior commit count (repo age), subject
  token count (request detail), bot flag. Bots are also excluded in a
  robustness row.

## Honest limitations

1. **The target is change size (files touched), not person-days.** L4
   (size -> days) and L5 (friction -> days) are **not** measurable from
   public data: no dataset pairs repository signals with logged effort at
   task level. Those links remain an explicit assumption.
2. **git-only friction**: 2 of 5 components. `fan_in`, `complexity` and
   `coverage_gap` are absent here, so the measured score is not the
   product's score (it is a lower-dimensional version of it).
3. **Commits are a request proxy.** A commit subject is not a client RFP;
   the product's unit is a project, this experiment's unit is a change.
4. **OSS != B2B SaaS.** Public Python libraries; nothing here validates
   client delivery estimation directly.
5. **Tercile cuts are sample-dependent**, so L2's ratio is not a universal
   constant — it is a measured, repo-conditioned quantity.
6. Blobless clones carry no line counts, so size is files touched only.
